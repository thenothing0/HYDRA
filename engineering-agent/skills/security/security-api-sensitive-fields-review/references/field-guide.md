# API response-property authorization — decision procedure

## Establish the boundary

Build role-to-readable-field rules from the product contract, then trace serializers, projections, GraphQL fields, exports and nested relationships. Separate rightful object access from authority over each sensitive property.

## Smallest decisive verification

Use a synthetic object with public and restricted canaries. Compare response fields for an allowed object viewer and an entitled field reader; inspect actual serialized bytes and alternate representations.

## Reject or narrow unsupported conclusions

A UI-hidden field, undocumented attribute or owner-visible field is not automatically unauthorized exposure. Determine sensitivity and policy; do not infer write access from a read leak.

If the boundary is absent, record not-applicable and the reason. If an artifact/access requirement is missing, name that missing decisive check and keep the hypothesis unverified. Observed behavior must match the claimed actor/build/resource; a fixture only proves its encoded boundary. Stop on unexpected unrelated effects or degradation.

## Repair acceptance

Apply role-appropriate server projections/field resolvers and test all evidenced representations. Retest allowed fields, denied restricted fields and preservation of legitimate export/query behavior.

## Evidence worksheet

object permission; field classification/policy; serializer/resolver path; role-specific synthetic responses; nested/export variants; actual disclosure and allowed-field control

Each result should explain the intended policy, caller control, actual consumer, result and competing explanation. Severity follows the evidenced consequence and prerequisites, not the technique label.
