# Protocol, intermediary and origin trust

Analyst decision guide for this family. Use the questions relevant to the actual skill/target; this is not a certification checklist or evidence that any check occurred.

Draw the actual hop chain and identify who controls each authority, routing and protocol field. Record server/proxy/parser/receiver versions and current protocol semantics. A request header naming an origin or internal role does not authenticate its source.

Choose a hypothesis at a known boundary: framing disagreement, authority used to build a sensitive URL, server-side destination policy, dangling provider binding or mail-domain alignment. Prefer local replicas/passive owner evidence; avoid broad discovery, shared-connection desynchronization or unsolicited mail.

Compare raw and canonical representations and establish which consumer actually acted. Errors, DNS names, SPF pass without author-domain alignment, cache status and public redirects do not prove the stronger private-data or authority claim. Resolver/provider/receiver behavior and ownership constraints matter.

Repair the authoritative parsing, trust, destination or resource-binding decision and retest the intended protocol use plus the prohibited variant. Keep a local model, configuration prediction and measured deployment result distinct. A provider resource is not yours to claim because a DNS record looks stale.

## Evidence before conclusion

- hop/protocol/version and field provenance
- owner/asset/action and normalization/destination contract
- actual consumer and bounded raw/protocol evidence
- benign alternative and receiver/provider limits
- valid protocol use and rejected-variant retests

Use the technique-specific guide and current primary runtime/provider documentation for details. If a decisive requirement is unavailable, record the missing artifact and narrower supported conclusion.
