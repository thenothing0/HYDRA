# Data, grammar and interpreter authority

Analyst decision guide for this family. Use the questions relevant to the actual skill/target; this is not a certification checklist or evidence that any check occurred.

Trace untrusted input through every decoding/coercion/merge to the exact interpreter API. Distinguish bound values from structure: SQL identifiers/operators, command options, LDAP filter versus DN, XPath expression, template source, mail headers/envelope and exported spreadsheet cell boundaries need different handling.

Prove semantic control in an isolated fixture or a complete source path. Prefer inert argv/query/constructor/DOM markers and synthetic rows/cells over side-effect payloads. Establish actual interpreter version/context and the privileged consumer. A parser error, reflected delimiter or suspicious library call is not sufficient.

Compare valid structured features and literal hostile-looking data with the candidate effect. Schemas, escaping and sanitizers are context-specific. A shell-free process still needs safe options; a CSV parser is not a spreadsheet formula interpreter; a trusted signature is not a safe deserializer.

Repair the actual boundary with supported data APIs, constrained structure or narrowly justified interpreter capabilities. Retest valid Unicode/quotes/paths/queries and the original prohibited semantics. Keep a primitive distinct from unverified account takeover, code execution or exfiltration.

## Evidence before conclusion

- untrusted source, transformations and exact grammar context
- binding/structure and authority contract
- actual interpreter/consumer and original code location
- minimal semantic effect and competing benign explanation
- context-correct repair and legitimate syntax controls

Use the technique-specific guide and current primary runtime/provider documentation for details. If a decisive requirement is unavailable, record the missing artifact and narrower supported conclusion.
