# security-background-job-authorization-review: investigative procedure

This is an authored decision procedure, not an executed target assessment or a universal test list. Adapt the concrete fixture to the user's actual feature. Preserve authorization already established; a missing live capability does not prevent source analysis.

## Open these artifacts first

Read enqueue, worker, job-status and result-download code together. Record requester identity, resource references, service credentials, grant lifetime and the policy for revoked membership.

## Decisive experiment and source trace

Queue an A-owned export referring to private synthetic B data. Determine whether the worker re-establishes the caller's permitted resource set or trusts a supplied tenant/user field. Separately inspect whether A can read B's existing job/result. For revocation, use the product's declared enqueue-time versus execution-time grant rule.

For source-only work, identify the entry, transformations, authoritative check and protected consumer in the actual build. Record file/line or artifact locations for each material edge. Do not invent a dynamic observation from that trace.

## Evidence that rejects or narrows the hypothesis

A privileged worker is normal architecture. Job acceptance without forbidden consumption is not an export leak. A policy intentionally granting an immutable snapshot must not be labeled stale authorization solely because membership later changes.

## Repair acceptance

Bind requester, referenced objects and result owner; enforce the declared grant lifetime at consumption. Retest result URLs/status as well as the job action and legitimate delayed processing.

## When the next edge is unavailable

If the grant lifetime is unknown, ask that narrow policy question and keep revocation behavior unresolved while reviewing ordinary cross-tenant binding.

## Deliver a decision, not a checklist count

Write the actual policy, attacker-controlled input, check-to-consumer trace, observed or source-supported effect, legitimate control and remaining gap. Use the existing finding template only for a supported independent root cause; keep inventory and rejected hypotheses in the assessment notes. If an experiment is run, record its build, input, output and side effects. A suggested experiment in this file is not evidence that it ran.

Use [runtime capabilities](runtime-contract.md) only when host/tool differences matter. Primary technical references remain in the entrypoint and any existing technique guide.
