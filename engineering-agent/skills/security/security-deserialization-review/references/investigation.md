# security-deserialization-review: investigative procedure

This is an authored decision procedure, not an executed target assessment or a universal test list. Adapt the concrete fixture to the user's actual feature. Preserve authorization already established; a missing live capability does not prevent source analysis.

## Open these artifacts first

Trace input bytes through format detection, decompression, nested decoding and runtime object/type construction. Record trust/signature checks before deserialization and available type restrictions.

## Decisive experiment and source trace

In an isolated fixture use an inert type/constructor marker to determine whether caller-selected types or hooks are instantiated. Inspect formats statically when loading would run code; gadget execution is unnecessary to prove an unsafe trust boundary.

For source-only work, identify the entry, transformations, authoritative check and protected consumer in the actual build. Record file/line or artifact locations for each material edge. Do not invent a dynamic observation from that trace.

## Evidence that rejects or narrows the hypothesis

JSON parsing into plain data is not automatically unsafe deserialization. A signed envelope only changes the conclusion if signature verification and the authorized producer boundary actually protect these exact bytes before loading.

## Repair acceptance

Use a data-only format or supported restricted loading with explicit schema/type authority. Retest normal data, rejected unexpected types and nested decoder paths.

## When the next edge is unavailable

Without loader/version or producer trust evidence, record the candidate format and missing trust edge. Never load an unknown artifact merely to discover its contents.

## Deliver a decision, not a checklist count

Write the actual policy, attacker-controlled input, check-to-consumer trace, observed or source-supported effect, legitimate control and remaining gap. Use the existing finding template only for a supported independent root cause; keep inventory and rejected hypotheses in the assessment notes. If an experiment is run, record its build, input, output and side effects. A suggested experiment in this file is not evidence that it ran.

The [family guide](decision-playbook.md) is optional for cross-cutting context; the technique procedure above is the starting point. Use [runtime capabilities](runtime-contract.md) only when host/tool differences matter. Primary technical references remain in the entrypoint and any existing technique guide.
