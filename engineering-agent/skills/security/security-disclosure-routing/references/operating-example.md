# Resolve the owner before choosing a platform

## A concrete ownership ambiguity

An affected application uses a CDN, an identity provider and a hosted database. Its public hostname points to the CDN. If the flaw is the application's export authorization, a CDN CNAME does not make it a CDN-program finding. Establish the application operator's official policy and its designated program. If the defect is in vendor-distributed software, distinguish the affected deployment from the vendor product/version and verify the vendor's own channel.

Use the official owner page to find candidate routes, then the actual current program brief to bind exact asset, issue class, account access and exclusions. Record the relevant quoted clause or concise sourced paraphrase and checked time. A directory listing or security.txt Contact alone is a pointer. A wildcard scope entry must be interpreted with its actual exclusions and program text; do not infer parent/subdomain coverage from string similarity.

## Handle conflicting evidence

If the owner page names an inactive program while another platform lists the brand, preserve both sources and leave the route unresolved. Request only the missing authoritative brief/access evidence; keep writing a neutral technical report meanwhile. For a private program, do not invent its asset list from public search. Before any already-authorized transmission, recheck the chosen route's live status and required form.

Deliver one route record per finding: responsible owner, exact asset/product, official source chain, scope/type rationale, available access, channel and remaining blocker. A local training service has no external program: its correct route is unresolved/local exercise, not a guessed HackerOne destination.
